## 1. Паспорт приложения

- **Название:** Follow Up Boss Connector
- **Короткое описание:** Полный коннектор к Follow Up Boss (FUB) — ведущей CRM для агентов и команд недвижимости в США (Zillow Group). Управление контактами (People), сделками (Deals/Pipelines), звонками, задачами, заметками, встречами, SMS/email-шаблонами, командами, кастомными полями, вебхуками, Automations 2.0 и Smart Lists прямо из Imperal.
- **Почему сейчас:** прямое поручение Влада — «Follow Up Boss - разработай это приложение в максимальной форме со всеми доступными функциями с их стороны и всеми возможными функциями внутри нашего приложения для повышения эффективности» (см. Vikunja #2284, создан по шаблону #2149/#2143).
- **Связанное событие/цель:** расширение портфеля Imperal Apps вертикальными CRM для конкретных ниш (рядом с общими CRM HubSpot/Salesforce) — real estate — одна из крупнейших вертикалей для малого и среднего бизнеса.

## 2. Проблема в человеческих словах

Когда **агент или брокер недвижимости** сталкивается с необходимостью **быстро реагировать на входящий лид, вести его через воронку (New Lead → Contacted → Nurture → Under Contract → Closed) и не терять ни одного касания (звонок/SMS/email/встреча)**, ему приходится **вручную переключаться между FUB-интерфейсом, телефоном и почтой, вручную создавать задачи по каждому лиду, вручную проверять кто из агентов просрочил звонок, вручную собирать сводки по Pipeline для брокера**, из-за чего возникает **потеря скорости реакции на лид (доказанно критичный фактор конверсии в real estate — по отраслевым данным первые 5 минут решают всё), пропущенные follow-up'ы и отсутствие единой картины здоровья pipeline у брокера**.

Существующие инструменты (сам FUB UI) хорошо решают операционную часть для одного агента внутри их приложения, но не дают:
- программного массового аудита (кто просрочил задачи, чьи лиды "зависли" без контакта N дней);
- единого места, где агентство одновременно работает с FUB, WordPress-сайтом, почтой, Slack и другими инструментами через один AI-слой;
- быстрых batch-операций (переназначить N лидов, тегировать пачкой, обновить стадии пачкой) без ручного клика по каждому контакту в UI.

## 3. Кто пользователь и какие роли

По ролевой модели самого FUB (см. `CONNECTOR_DISCOVERY.md` §2):

- **Owner** — полный доступ, включая Webhooks и Automations. Основной профиль пользователя, подключающего коннектор.
- **Admin/Broker** — почти всё, кроме Webhooks. Коннектор должен явно и по-человечески объяснять 403 на webhook-функциях для этой роли — это не баг, а особенность прав ключа.
- **Agent** — доступ только к своим назначенным контактам, ограниченный доступ к Automations. Коннектор работает и для агента, но с урезанным охватом данных — тоже не баг.
- **Lender** — аналогично агенту, для ипотечных партнёров.

**Решение (Влад, неявно через объём поручения "максимальная форма"):** коннектор поддерживает все 4 роли прозрачно — ошибки прав FUB транслируются в понятные сообщения ("эта функция доступна только владельцу аккаунта FUB"), а не как внутренний сбой.

## 4. Ключевые архитектурные решения

### 4.1 Авторизация — Basic Auth с API Key (не OAuth) как основной путь

FUB поддерживает и Basic Auth через персональный API Key, и OAuth2. Для коннектора «один пользователь управляет своим аккаунтом» (тот же паттерн, что HubSpot Private App Token, Klaviyo API Key, PagerDuty REST API key) — **Basic Auth с API Key выбран как единственный путь v1**:

- `connect_followupboss(api_key, label?)` — сохраняет ключ, сразу проверяет его вызовом `GET /v1/identity` (Basic Auth: `api_key` как username, пустой password).
- OAuth2-путь (`docs.followupboss.com/docs/getting-started-with-oauth`) НЕ реализуется в v1 — он предназначен для сторонних маркетплейс-интеграций с множественными пользователями/приложениями (аналог PagerDuty scoped OAuth для marketplace apps), что не соответствует модели "коннектор к своему аккаунту".

### 4.2 System Registration — сознательно НЕ блокирует v1

FUB даёт повышенные rate-limit'ы и доступ к ряду ресурсов (Automations, Attachments, Inbox Apps) только зарегистрированным системам (заголовки `X-System` + `X-System-Key`, требует email-заявку в FUB support). Это внешний процесс с непредсказуемым SLA стороннего вендора.

**Решение:** v1 коннектора работает БЕЗ регистрации системы — на базовых (более низких) rate-limit'ах, и в тех разделах, что требуют System Key, выдаёт понятную ошибку с указанием, что для этой функции нужна регистрация системы у FUB. Функции, доступные только зарегистрированным системам, помечены в `CONNECTOR_DISCOVERY.md` явно (Automations write-операции, Attachments, Inbox Apps) — они всё равно реализуются в коде (чтобы работать сразу, как только Влад решит подать заявку на регистрацию), но задокументированы как условно рабочие.

### 4.3 Rate limiting — общий retry-хелпер

Скользящее окно 10 секунд, контекстное (`global`, `events`, и т.д.), ответ `429` + заголовок `Retry-After`. Клиент реализует один общий `_request()` с уважением к `Retry-After` и единичным авто-retry — тот же паттерн, что уже есть в PagerDuty/DocuSign коннекторах.

### 4.4 Automations 2.0 vs legacy Action Plans

FUB мигрирует Action Plans → Automations 2.0. **Решение:** реализуем актуальный `/automations` API как основной, но оставляем legacy `/actionPlans` (read + apply-to-person) как доступный резерв для аккаунтов, ещё не мигрированных FUB — оба слоя присутствуют, потому что миграция управляется самим FUB не одномоментно для всех клиентов.

### 4.5 Custom Fields quirk

Чтение custom fields на `peopleUpdated`-событиях требует явного query-параметра (`?fields=allFields`, по докам webhook guide) — иначе кастомные поля не приходят по умолчанию. Отражено в discovery как явная ловушка для webhook-обработчика.

## 5. Объём релиза — Ярус 1+2+3 (максимум, по прямому поручению)

См. `CONNECTOR_DISCOVERY.md` §3 для полного постатейного списка по всем ресурсам: People (+Relationships +Reactions), Deals+Pipelines+Stages, Calls, Tasks, Notes, Text Messages+Templates, Email Templates, Appointments+Types+Outcomes, Events (lead intake), Users, Teams/Groups/Ponds, Automations 2.0 + legacy Action Plans, Custom Fields, Smart Lists, Webhooks, Identity, System registration.

Итого ориентировочно ~90-100 функций, из которых на нашей стороне поверх голого API добавляются value-add функции повышения эффективности:

- `audit_pipeline_health` — агрегированный отчёт: сколько лидов без контакта >N дней, сколько просроченных задач по агенту, распределение по стадиям.
- `find_stale_leads` — лиды без активности дольше порога.
- `bulk_reassign_people` / `bulk_tag_people` / `bulk_update_stage` — пакетные операции по явному списку id (аналог `bulk_update_deal_stage` в HubSpot-коннекторе).
- `get_agent_response_time_report` — среднее время первого контакта по агенту (используя Calls+Notes+TextMessages timestamps относительно `createdAt` контакта) — прямое попадание в "первые 5 минут решают всё" боль индустрии.

## 6. UI — обязательные правила (см. `Docs/session-notes/UI_INTERFACE_STANDARD.md`)

- Единственная кнопка "App settings" в левом сайдбаре, открывающая `panels_settings.py` (отдельный файл центрального слота) — без дублирования инструкций между сайдбаром и модалкой.
- Все инпуты — с лейблами; плейсхолдер — контекстно уместный текст примера (не название поля).
- Контейнер формы принудительно растянут на всю ширину левого сайдбара; содержимое формы растянуто на всю ширину контейнера.
- Инструкция по кнопке живёт в модалке/тултипе этой кнопки — не дублируется прозой в сайдбаре.
